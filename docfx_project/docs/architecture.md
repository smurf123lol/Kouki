### 1. Общая концепция

Kouki — это модульная платформа для оркестрации команд, предназначенная для встраивания в AI-агенты, голосовые ассистенты, CLI-утилиты, веб-сервисы и автоматизированные системы. Она состоит из трёх основных уровней:

- **Mugura** — чистое ядро оркестрации. Регистрирует команды через атрибуты, управляет их жизненным циклом, вызывает хендлеры в изолированных DI-скоупах. Не зависит от окружения (файловая система, терминал, сеть).
- **Shimi** — слой абстракций и адаптеров. Определяет интерфейсы для работы с окружением (файловая система, терминал, хранилище, логирование) и предоставляет механизм контекстов выполнения (`IExecutionContext`, `IContextRegistry`). Разделён на `Abstractions` (только интерфейсы) и `Context` (реализации реестра и базового контекста).
- **Ubusuna** — библиотека расширений, содержащая готовые адаптеры (консольные, HTTP, FTP), конкретные контексты, дополнительные роутеры (`RemoteRouter`, `MushiRouter`, `DelegatingRouter`) и фабрики. Подключается одной строкой через `AddUbusuna()`. //todo: delegatingrouter по находится в mugura

Такое разделение обеспечивает гибкость, переиспользуемость и тестируемость.

### 2. Mugura (ядро)

#### 2.1. Назначение

- Регистрация команд через атрибут `[Command]` на классах-хендлерах.
- Оркестрация вызова: от имени команды до выполнения хендлера.
- Управление временем жизни: каждый вызов выполняется в своём DI-скоупе (изоляция зависимостей).
- Единый формат ввода/вывода: входной аргумент — `JsonNode?`, выход — `JsonNode` (может быть любым JSON-совместимым значением). Внутри ядра аргумент десериализуется в строго типизированный DTO команды.
- Базовая валидация DTO через `System.ComponentModel.DataAnnotations` (с возможностью расширения кастомными атрибутами из внешних библиотек).

#### 2.2. Ключевые компоненты

- **`CommandAttribute`** — применяется к хендлеру. Содержит имя команды, описание, категорию (битовые флаги), флаг подтверждения и пример.
- **`CommandRegistry`** — сканирует сборки, находит хендлеры с атрибутом, извлекает DTO команды, собирает правила валидации из атрибутов свойств DTO. Хранит записи `CommandEntry` в словарях по имени и по типу DTO.
- **`CommandEntry`** — запись с полями: `CommandType`, `HandlerType`, `Name`, `Description`, `Category`, `ValidationRules`, `Example`.
- **`ICommandFactory`** — фабрика для создания DTO из `JsonNode`. Содержит generic-метод `CreateCommand<TCommand>`; сама фабрика не generic. Использует `JsonSerializer.Deserialize` для десериализации.
- **`ICommandValidator<TCommand>`** — интерфейс валидатора. Реализация по умолчанию — `DataAnnotationsValidator<TCommand>`, использующая правила из `CommandEntry` (полученные через `CommandRegistry`). Может быть переопределена для конкретной команды через DI.
- **`IScopeManager`** / **`ScopeManager`** — управляет созданием DI-скоупов для каждого вызова команды.
- **`ICommandDispatcher`** — generic-метод `SendAsync<TCommand>`, внутри скоупа получает хендлер `ICommandHandler<TCommand>` и вызывает его.
- **`IRouter`** — интерфейс для маршрутизации. Основная реализация — `StaticRouter`.
- **`StaticRouter`** — локальный исполнительный роутер. По имени команды находит `CommandEntry`, создаёт DTO через фабрику, применяет валидатор (если зарегистрирован), затем вызывает диспетчер. Кеширует делегаты для вызова валидатора и диспетчера по типу команды для производительности.
- **`DelegatingRouter`** — абстрактный базовый класс для роутеров-обёрток, которые делегируют выполнение внутреннему роутеру. Упрощает создание новых типов роутеров (например, `IntentRouter`, `RemoteRouter`).
- **Метод расширения `AddMugura`** — регистрирует все компоненты ядра в DI (синглтоны), сканирует сборки и регистрирует хендлеры как Scoped.

#### 2.3. Поток вызова (статический роутер)

1. Внешний код вызывает `IRouter.RouteAsync(commandName, argument, context?)`.
2. `StaticRouter` получает `CommandEntry` из `CommandRegistry`.
3. Фабрика создаёт DTO команды из `JsonNode`.
4. Если зарегистрирован валидатор, он проверяет DTO; при ошибке возвращается `JsonNode` с ошибкой.
5. Диспетчер создаёт скоуп, получает хендлер и вызывает `HandleAsync`.
6. Хендлер выполняет бизнес-логику, используя контекст (если передан) и сервисы из DI.
7. Результат (JsonNode) возвращается обратно.

### 3. Shimi (абстракции и контексты)

#### 3.1. Абстракции (Shimi.Abstractions)

Проект содержит только интерфейсы, без реализаций. Основные из них:

- **`IFileSystem`** — базовый интерфейс для работы с байтовыми данными: `ReadBytesAsync`, `WriteBytesAsync`, `ExistsAsync`, `GetTreeAsync`.
- **`ITextFileSystem`** — расширяет `IFileSystem`, добавляет методы для текстовых файлов (`ReadTextAsync`, `WriteTextAsync`, `AppendTextAsync`) с параметром `Encoding`.
- **`IJsonFileSystem`** — расширяет `IFileSystem`, добавляет методы для JSON-сериализации (`ReadJsonAsync`, `WriteJsonAsync`) с параметрами `JsonSerializerOptions`.
- **`IStateStore`** — хранилище ключ-значение для состояния.
- **`ITelemetryLogger`** — логирование событий и ошибок.
- **`IExecutionContext`** — контекст выполнения, содержащий конкретные реализации `IFileSystem`, `ITerminal`, `IStateStore` и доступ к дополнительным сервисам через `GetService<T>()`. Имеет свойство `Name` для идентификации.
- **`IContextRegistry`** — реестр предопределённых контекстов. Позволяет регистрировать контексты по имени, устанавливать и получать контекст по умолчанию.

#### 3.2. Контексты (Shimi.Context)
//todo
Содержит реализации:

- **`ContextRegistry`** — синглтон, хранит словарь контекстов. Методы: `RegisterContext`, `GetContext`, `SetDefaultContext` (по экземпляру или по имени), `GetDefaultContext`.
- **`BaseExecutionContext`** — абстрактный базовый класс для контекстов. Хранит имя и словарь дополнительных сервисов. Предоставляет реализацию `GetService<T>()`. Конкретные контексты должны переопределять свойства `FileSystem`, `Terminal`, `StateStore`.
- **`InMemoryStateStore`** — базовая реализация `IStateStore` в памяти (опционально).
- **Метод расширения `AddShimiContext`** — регистрирует `IContextRegistry` и `IStateStore` (можно переопределить).

Важно: `Shimi.Context` **не создаёт** дефолтный контекст автоматически. Приложение должно явно установить его через `SetDefaultContext`.

### 4. Ubusuna (библиотека расширений)

`Kouki.Ubusuna` предоставляет готовые реализации адаптеров, контекстов, роутеров и фабрик, чтобы упростить подключение и настройку.

#### 4.1. Адаптеры
//todo
- **`ConsoleFileSystem`** — реализует `IFileSystem` (и опционально `ITextFileSystem`, `IJsonFileSystem`) для работы с локальной файловой системой через стандартные методы `System.IO`. Поддерживает работу с корневым каталогом.
- **`ConsoleTerminal`** — реализует `ITerminal`, запускает внешние процессы через `System.Diagnostics.Process`.
- **`HttpFileSystem`**, **`FtpFileSystem`** — (планируются) для работы с удалёнными файловыми хранилищами.

#### 4.2. Контексты

- **`ConsoleExecutionContext`** — конкретный контекст с консольными адаптерами (`ConsoleFileSystem`, `ConsoleTerminal`, `InMemoryStateStore`).
- **`ObsidianExecutionContext`** — (планируется) для интеграции с Obsidian API.

#### 4.3. Роутеры
//todo
- **`DelegatingRouter`** — абстрактный базовый класс (может быть перенесён в ядро или оставлен в Ubusuna). Реализует `IRouter`, принимает внутренний роутер в конструкторе и делегирует ему выполнение. Наследники могут переопределить логику.
- **`RemoteRouter`** — отправляет команды по сети (HTTP, gRPC) на удалённый сервер.
- **`MushiRouter`** — композитный роутер, последовательно пробует список внутренних роутеров до первого успешного выполнения.

#### 4.4. Фабрики и DI

- **`AddUbusuna(this IServiceCollection, Action<UbusunaOptions>?)`** — регистрирует все стандартные адаптеры, контексты и роутеры. Позволяет через опции выбрать, какие адаптеры использовать, зарегистрировать предопределённые контексты и настроить роутинг.

Пример использования:

```csharp
services.AddShimiContext();
services.AddUbusuna(options =>
{
    options.UseConsoleAdapters();
    options.SetDefaultContext("console");
    options.AddContext("admin", adminFs, adminTerminal);
    options.UseMushiRouter(); // или UseRemoteRouter, UseStaticRouter
});
```

### 5. Взаимодействие с голосовым ассистентом (IntentRouter)
//TODO
`IntentRouter` — это внешняя реализация `IRouter`, живущая в приложении (например, в `Kagedama.Voice`). Она использует каскадную систему определения интента:

- **ML.NET / fastText** — быстрый уровень, ранжирует все интенты, выдаёт топ-10 кандидатов.
- **BERT / Sentence-BERT** — точный уровень, переранжирует кандидатов и выбирает лучший с оценкой уверенности.
- **LLM (GPT) или уточнение у пользователя** — резервный уровень, если уверенность BERT ниже порога.

`IntentRouter` извлекает слоты (аргументы) через Cross-Encoder или NER-модель, формирует `JsonNode` с аргументами и вызывает внутренний роутер (обычно `StaticRouter` или `MushiRouter`) для выполнения команды. Логирование отказов и успехов происходит через `ITelemetryLogger`.

---

### 6. Расширение роутинга (MushiRouter)

`MushiRouter` — композитный роутер, реализующий `IRouter`. Он принимает список внутренних роутеров и последовательно вызывает их до первого успешного выполнения. Это позволяет комбинировать локальный `StaticRouter`, `IntentRouter`, `RemoteRouter` и другие. Например, можно попробовать сначала `IntentRouter` (для голосовых команд), затем `RemoteRouter` (для удалённых), и только потом `StaticRouter`.

### 7. Преимущества разделения

- **Чистое ядро** — `Mugura` не зависит от окружения, легко тестируется, может использоваться в любых средах.
- **Гибкие адаптеры** — `Shimi` предоставляет интерфейсы, а конкретные реализации подключаются через `Ubusuna` или приложение.
- **Контексты выполнения** — позволяют переключать реализации сервисов (например, файловую систему) в зависимости от пользователя, проекта или окружения без изменения кода хендлеров.
- **Модульные расширения** — `Ubusuna` предоставляет готовые компоненты, но их можно заменить своими.
- **Единый формат ввода/вывода** (JsonNode) упрощает интеграцию.
- **DI-дружественность** — всё собирается через стандартный контейнер.

### 8. Рекомендации по использованию

Для нового приложения:

1. Добавить ссылки на `Kouki.Mugura`, `Shimi.Abstractions`, `Shimi.Context`, `Kouki.Ubusuna`.
2. В DI вызвать `AddShimiContext()` и `AddUbusuna()` с нужными опциями.
3. Написать хендлеры, помеченные `[Command]`.
4. В точке входа (MCP, CLI, HTTP, голос) вызвать `IRouter.RouteAsync` с именем команды, `JsonNode` аргументами и, при необходимости, контекстом.

Для удалённого взаимодействия использовать `RemoteRouter` и `MushiRouter` для композиции.
