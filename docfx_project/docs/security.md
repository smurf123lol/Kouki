# Безопасность сервера

Этот документ отвечает на два вопроса: **от кого защищаемся** и **что уже сделано, а что
осознанно не сделано**. Он же — чек-лист перед тем, как выставлять Kouki в сеть, отличную
от домашней.

## Модель угроз

Сервер рассчитан на **локальную сеть** и одного-двух владельцев. Это не публичный сервис,
и относиться к нему как к публичному нельзя.

| Актив | Почему важен |
| --- | --- |
| Задачи и журнал разбора | личные планы и формулировки, история фраз |
| Аудиозаписи (`audio/`) | голос человека — это персональные данные |
| Bearer-токен | кто его знает, тот может исполнять команды |
| База `kouki.sqlite` | всё вышеперечисленное в одном файле |

| Противник | Что может | Чем закрываемся |
| --- | --- | --- |
| Сосед по Wi-Fi | отправлять команды, читать задачи | bearer-токен, fail-closed авторизация |
| Случайный сканер из интернета | то же, если порт проброшен | не выставлять наружу; reverse-proxy с TLS, если очень нужно |
| Человек с доступом к файлам сервера | читать базу и аудио | права файлов на уровне ОС; шифрование диска средствами ОС |
| Человек с доступом к плате | читать `sdkconfig.secret` (Wi-Fi, токен) | отдельный токен на плату, ротация, отдельный Wi-Fi/VLAN |

## Что сделано

- **Авторизация fail-closed.** Пустой `Kouki:Token` — ошибка запуска, а не «пускаем всех».
  Открытый режим — только явный `Kouki:AllowAnonymous=true` (для локальной отладки).
  Отказ приходит как `401` с `WWW-Authenticate: Bearer realm="kouki"`, попытки пишутся в лог
  (первая и каждая сотая — чтобы не залить лог мусором).
- **Заголовки безопасности.** `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`,
  `X-Frame-Options: DENY` и CSP `default-src 'self'` — на статике и на API, включая 401.
- **Ограничение частоты.** 120 запросов в минуту на токен (или адрес, если токена нет);
  `/api/health` не ограничивается, чтобы мониторинг не упирался в 429.
- **Лимиты входа.** Размер записи (`Kouki:MaxVoiceBytes`, `MaxVoiceSeconds`), длина текста
  (`Kouki:MaxTextLength`), `Content-Type` проверяется до разбора тела; мусорный WAV —
  `415`, слишком длинный текст — `400`.
- **Разбор ответов Telegram Bot API** — по коду, а не «успех = JSON»; тело ошибки не уходит
  человеку в чат как есть.
- **Срок хранения аудио** — настройка: `AudioRetentionDays` (30) и
  `AudioLabeledRetentionDays` (90; `0` — не удалять размеченное). Чистка идёт фоном.
- **Журналы вместо тишины.** `/api/actions` знает, кто и что сделал; HTTP-лог знает, какой
  запрос был отклонён, и с каким кодом.
- **Секреты не в git.** `appsettings.json` — без токенов, `firmware/sdkconfig.secret` —
  в `.gitignore` (в образ станции секреты всё равно попадают — см. ниже).

## Что осознанно не сделано

| Не сделано | Почему | Что делать, если нужно |
| --- | --- | --- |
| Нет TLS | сервер живёт в локальной сети; сертификат на голый HTTP-порт ничего не даёт | поставить Caddy/nginx перед сервером; для станции — Caddy в локальной сети и **сертификат, вшитый в прошивку** (T55) |
| Нет пользователей и ролей | один владелец — один токен | отдельные токены на хосты (станция, бот, дашборд) + reverse-proxy с аутентификацией |
| Нет шифрования базы | SQLite + локальный диск | шифрование диска ОС (LUKS) |
| Секреты в образе станции | NVS-провижининг не сделан | T46: заливать Wi-Fi и токен в NVS при прошивке, а не в `sdkconfig.secret` |
| Нет secure boot станции | вне задачи | по необходимости, вместе с провижинингом |

## Как запускать безопасно

1. **Токен.** Свой, длинный, не из примеров: `Kouki:Token` (или `KOUKI_TOKEN` через
   `tools/run-server.ps1`). Токен — не пароль от чего-то ещё.
2. **Сеть.** Домашняя LAN. Если сервер ставится на машину с внешним доступом — только через
   reverse-proxy с TLS и запретом доступа к `/api/*` снаружи без токена.
3. **Права файлов.** База и `audio/` — только владельцу (`chmod 600`/`700`), бэкап с теми же
   правами.
4. **Ротация.** Меняете токен — перепрошейте станцию (в её образе старый токен) и обновите
   бота и дашборд.
5. **Не коммитить.** `sdkconfig.secret`, `.env`, базы и аудио — в `.gitignore`, проверять
   `git status` перед коммитом.

## Если появится публичный доступ

Порядок, который дешевле, чем разбираться после: reverse-proxy с TLS → отдельные токены на
каждого клиента → ограничение частоты на прокси → отдельная база и каталог аудио →
бэкапы с проверкой восстановления. Только после этого имеет смысл говорить о «сервере в
интернете», а не «сервере в квартире».
